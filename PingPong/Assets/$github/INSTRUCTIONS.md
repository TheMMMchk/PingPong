# Общая инструкция для ИИ по Unity-проектам

## Назначение

Эта инструкция является общей для Unity-проектов пользователя.

Она **не описывает конкретную игру** и не должна привязывать ИИ к конкретным названиям классов, механикам или структуре одного проекта.

Главная задача инструкции: помогать ИИ сохранять единый подход к разработке во всех проектах пользователя.

---

## 1. Главный принцип

При работе над проектом ИИ должен в первую очередь изучать **сам проект как источник архитектурных решений**.

Если существующая архитектура проекта уже решает похожую задачу, новый код должен следовать тому же подходу.

Не следует без причины заменять существующий стиль на другой архитектурный подход только потому, что он считается более современным, универсальным или теоретически более правильным.

### Приоритеты

1. Понятность.
2. Соответствие существующей архитектуре проекта.
3. Простота.
4. Минимальное количество изменений.
5. Надёжность и поддерживаемость.

---

## 2. Проект является примером архитектуры

Существующий код проекта следует рассматривать не только как код, который нужно изменить, но и как **пример архитектуры, которую пользователь выбрал для проекта**.

ИИ должен обращать внимание на:

- расположение скриптов;
- разделение систем;
- ответственность классов;
- способы взаимодействия между компонентами;
- именование;
- организацию папок;
- используемые Unity-компоненты;
- существующие способы хранения состояния и данных.

Если проект уже имеет понятный способ организации функциональности, новый функционал должен по возможности использовать этот способ.

---

## 3. Не ломать архитектуру без необходимости

Не следует:

- объединять несколько независимых систем в один большой класс;
- добавлять новую функциональность в случайный существующий скрипт;
- создавать глобальные менеджеры только ради удобства;
- вводить сложные паттерны без реальной необходимости;
- полностью переписывать рабочую систему ради небольшого изменения;
- менять структуру проекта без причины.

Если архитектурное изменение действительно необходимо, сначала нужно объяснить:

- что именно меняется;
- зачем это требуется;
- почему существующий подход недостаточен;
- какие части проекта затронет изменение.

---

## 4. Одна основная ответственность

По умолчанию каждый скрипт должен иметь **одну основную ответственность**.

Например:

- управление игроком;
- управление мячом;
- подсчёт очков;
- управление состоянием игры;
- работа с сохранениями;
- обработка конкретного типа взаимодействия.

Это не означает, что класс обязан содержать ровно один метод или одну маленькую функцию.

Главное правило: ответственность класса должна оставаться понятной.

---

## 5. Организация по функциональности

Если проект использует структуру, разделяющую код по функциональным областям, её следует сохранять.

Предпочтительно группировать связанные системы рядом друг с другом, а не создавать одну огромную папку со всеми скриптами.

При создании нового крупного функционального блока сначала определить, к какой функциональной области он относится.

Если существующая структура проекта использует другой принцип организации, следовать существующему принципу.

---

## 6. Минимальные изменения

При выполнении задачи изменяй только то, что действительно необходимо.

Не следует одновременно:

- переписывать соседние системы;
- переименовывать множество файлов;
- менять стиль всего проекта;
- проводить рефакторинг, который не связан с задачей;
- удалять рабочий код без необходимости.

Если во время работы обнаружена потенциальная проблема, которая не мешает текущей задаче, сначала сообщи о ней отдельно вместо автоматического изменения.

---

## 7. Работа с существующим кодом

Перед изменением существующего кода:

1. Найди связанные с задачей компоненты.
2. Изучи их взаимодействие.
3. Определи, где в текущей архитектуре должна находиться новая логика.
4. Проверь, нет ли уже существующей системы, которую можно использовать.
5. Только после этого предлагай изменение.

Не создавай новый класс, если существующий компонент уже явно предназначен для этой ответственности.

И наоборот: не перегружай существующий класс новой независимой ответственностью только ради уменьшения количества файлов.

---

## 8. Новая функциональность

Для новой системы сначала определить:

- какую ответственность она имеет;
- с какими существующими системами взаимодействует;
- где она должна находиться;
- нужен ли новый скрипт;
- можно ли реализовать её без изменения существующей архитектуры.

Если новый скрипт нужен, он должен иметь понятное назначение и понятное имя.

---

## 9. Код должен быть понятным

Предпочитать простой и читаемый код.

Не использовать сложные конструкции только для сокращения количества строк.

Если простой вариант решает задачу, он предпочтительнее сложного.

Не добавлять абстракции, интерфейсы, события, паттерны и дополнительные уровни архитектуры без практической причины.

При этом существующие архитектурные решения проекта не нужно упрощать или переписывать только ради соответствия этому правилу.

---

## 10. Unity

При работе с Unity:

- учитывать текущую версию Unity и настройки конкретного проекта;
- использовать существующие в проекте пакеты и системы;
- проверять настройки проекта перед использованием API;
- учитывать используемую систему ввода;
- не использовать устаревшие API, если проект уже использует современную альтернативу;
- не добавлять зависимости без необходимости.

Если в проекте уже используется конкретная Unity-система, сначала использовать её, а не вводить параллельную систему.

---

## 11. Объяснение решений

ИИ должен не просто выдавать код, а помогать пользователю понимать архитектуру.

При существенном изменении желательно кратко объяснить:

- что изменяется;
- почему это место выбрано;
- какие компоненты участвуют;
- как новая система взаимодействует с существующими.

Не нужно превращать каждую простую правку в длинную лекцию.

---

## 12. Формат помощи пользователю

Если пользователь изучает разработку, предпочтительно работать как наставник:

1. Сначала объяснить идею.
2. Затем показать необходимые изменения.
3. Указать, куда помещается каждый файл или компонент.
4. Объяснить важные части кода.
5. После этого предложить проверить результат.

Не следует без необходимости выдавать огромный объём кода, который пользователь не сможет понять.

---

## 13. Если запрос недостаточно определён

Если из запроса невозможно однозначно понять:

- что именно должно происходить;
- где должна находиться новая система;
- какое поведение ожидается;
- нужно ли менять существующую архитектуру,

сначала задать уточняющий вопрос.

Не делать крупные архитектурные предположения без необходимости.

---

## 14. Конфликт между инструкцией и проектом

Эта инструкция является общей.

Если конкретный проект уже содержит явно сформированный архитектурный подход, **приоритет имеет существующая архитектура проекта**, если она не противоречит прямому требованию пользователя.

Если пользователь явно просит изменить архитектурный подход, следовать его запросу и учитывать последствия изменения.

---

## 15. Главное правило

> **Не пытайся сделать проект похожим на идеальную архитектуру из учебника. Помогай развивать архитектуру, которая уже существует в проекте и которую выбрал пользователь.**

Сначала изучи проект.

Потом пойми его архитектуру.

Потом предложи минимальное и понятное изменение.

И только после этого реализуй его.
