# Общая инструкция для ИИ по Unity-проектам

## Назначение

Эта инструкция задаёт предпочтительный архитектурный и объектно-ориентированный стиль разработки Unity-проектов пользователя.

Она должна работать и в существующем проекте, и в полностью новом пустом проекте.

В существующем проекте ИИ обязан сначала изучить реальную структуру и код и сохранить уже сформированные решения. В новом проекте эта инструкция является базовым стилем, пока пользователь не выбрал другой подход.

Главная цель - писать понятный, расширяемый код без архитектуры ради архитектуры и одновременно помогать пользователю изучать программирование.

## 1. Основные принципы

Приоритеты:

1. Понятность.
2. Соответствие архитектуре текущего проекта.
3. Простота.
4. Чёткое разделение ответственности.
5. Минимальное количество связанных изменений.
6. Расширяемость там, где она действительно нужна.
7. Обучаемость кода для пользователя.

Не следует выбирать архитектуру только потому, что она считается "правильной" или популярной.

Архитектура выбирается из задачи.

Не пытайся искусственно применить MVP, MVC, MVVM, ECS, Strategy, Factory или другой паттерн ко всему проекту.

## 2. Работа с существующим проектом

Перед изменением существующего функционала:

1. Найди связанные скрипты и компоненты.
2. Изучи их взаимодействие.
3. Определи существующие ответственности.
4. Посмотри, как похожие механики уже реализованы.
5. Определи место новой логики в текущей архитектуре.
6. Только после этого предлагай реализацию.

Если существующая архитектура уже решает похожую задачу, следуй ей.

Не переписывай рабочую систему только ради использования другого архитектурного подхода.

Если архитектурное изменение действительно необходимо, объясни:

- что меняется;
- зачем это нужно;
- почему текущий подход недостаточен;
- какие компоненты будут затронуты.

## 3. Архитектура строится от задачи

Для каждой новой механики сначала определить:

- какая у неё ответственность;
- какие данные ей нужны;
- кто управляет её состоянием;
- кто принимает решения;
- кто взаимодействует с игроком;
- что является Unity-технической частью;
- какие зависимости ей нужны.

После этого выбрать подход.

Паттерн не является целью сам по себе.

Если задача решается простым классом, не нужно создавать пять уровней абстракций.

Если задача действительно выигрывает от паттерна, использовать его и объяснить пользователю, почему он здесь подходит.

## 4. Одна основная ответственность класса

Каждый скрипт должен иметь одну понятную основную ответственность.

Класс может содержать несколько методов и работать с несколькими связанными данными, но его назначение должно легко объясняться одним предложением.

Плохой пример: GameManager, который одновременно управляет игроком, считает очки, сохраняет данные, запускает физику, управляет UI и создаёт врагов.

Предпочтительно разделять независимые ответственности.

При этом не нужно дробить код до абсурда. Несколько тесно связанных операций могут находиться в одном классе.

## 5. Предпочтение композиции и интерфейсов

Предпочтительный способ расширения поведения:

- композиция;
- зависимости;
- интерфейсы;
- небольшие независимые классы.

Не следует строить глубокую иерархию наследования без необходимости.

Наследование допустимо, когда отношение действительно является отношением "is-a" и оно упрощает архитектуру.

Интерфейс стоит использовать, когда нужно отделить контракт от реализации или предоставить несколько реализаций одного поведения.

Например, одна механика может получать действие через интерфейс, а конкретными реализациями могут быть управление игрока, управление бота и управление через тестовый источник.

Не создавать интерфейс просто потому, что "ООП требует интерфейсов".

## 6. Model

Model используется для состояния и правил конкретной механики, когда такое разделение полезно.

Model предпочтительно делать обычным C#-классом, а не MonoBehaviour, если ему не нужны:

- Unity lifecycle;
- Inspector;
- ссылка на объект сцены;
- Unity-компонент;
- другие специфические возможности MonoBehaviour.

Model должна защищать своё состояние.

Предпочтительно:

- private fields;
- public свойства или методы для контролируемого доступа;
- изменение состояния через методы класса;
- отсутствие случайного публичного изменения внутренних данных.

Model не должна становиться огромным контейнером для всей логики игры.

## 7. Controller

Controller используется, когда игрок или другой внешний источник напрямую влияет на механику.

Его задача - связать управляющее воздействие с механикой.

Например:

Input -> Controller -> Model -> View

Controller не должен автоматически становиться "главным менеджером" всей системы.

Если механика не требует такого слоя, не создавать Controller искусственно.

## 8. Service

Service используется для отдельной бизнес-логики конкретной механики.

Service не является универсальной папкой для "всего, что некуда положить".

Хороший Service:

- имеет конкретную ответственность;
- решает конкретную задачу;
- не зависит от Unity lifecycle без необходимости;
- может быть обычным C#-классом;
- может иметь несколько реализаций, если это действительно полезно.

## 9. View

View отвечает за Unity-представление и техническое взаимодействие с объектами сцены.

View может быть MonoBehaviour.

View может напрямую работать с Unity-компонентами, если это техническая часть поведения.

Например, допустимо напрямую использовать:

- Transform;
- Rigidbody / Rigidbody2D;
- Collider / Collider2D;
- Animator;
- AudioSource;
- ParticleSystem;
- Renderer;
- другие Unity-компоненты.

Не нужно создавать дополнительные Wrapper-классы только ради того, чтобы спрятать каждый Unity-компонент.

Особенно это относится к физике.

Если использование Rigidbody, Collider и других Unity-компонентов делает физическую механику понятнее и проще, использовать их напрямую.

При этом сложные правила игры и бизнес-логику по возможности не следует превращать в код MonoBehaviour только потому, что объект имеет Rigidbody.

## 10. MonoBehaviour

По умолчанию предпочтительны обычные C#-классы.

MonoBehaviour следует использовать, когда действительно нужны:

- Unity lifecycle;
- SerializeField и Inspector;
- ссылка на объект сцены;
- Unity Component API;
- физические компоненты;
- визуальное или аудио-представление;
- другие Unity-specific возможности.

Не следует делать каждый класс MonoBehaviour просто для удобства.

Если класс можно нормально создать через new и передать ему зависимости через конструктор, это предпочтительный вариант.

## 11. Unity-физика

Unity Physics является допустимой и предпочтительной частью технической реализации физики, если пользователь не просит реализовать физику самостоятельно.

Не нужно писать собственную систему столкновений, движения, гравитации или интеграции, если задача нормально решается через стандартные Unity-механизмы.

Пользователь пока имеет небольшой опыт самостоятельного создания физики, поэтому при работе с физикой ИИ должен:

1. Предпочитать стандартные Unity Physics-компоненты.
2. Объяснять важные настройки компонента.
3. Отделять игровое правило от технической физики, когда это возможно.
4. Не усложнять физику собственной математической системой без необходимости.
5. Если физический подход нетривиален, сначала кратко объяснить принцип.

Пример: Rigidbody2D может отвечать за физическое движение объекта, а отдельный класс - за правило "при попадании мяч должен изменить состояние игрока".

Это не означает, что Rigidbody обязательно нужно оборачивать в отдельный класс.

## 12. Bootstrap

Bootstrap является точкой сборки и запуска подсистемы.

Предпочтительный принцип:

Создание объектов и связывание зависимостей должно происходить через Bootstrap.

Bootstrap может:

- получить ссылки на Unity-компоненты через Inspector;
- создать обычные C#-классы;
- создать Model;
- создать Service;
- создать Controller;
- передать зависимости;
- запустить подсистему;
- вызывать необходимые Tick/Update-методы верхнего уровня.

По возможности зависимости должны передаваться явно.

Предпочтительно:

Bootstrap -> создание объектов -> constructor injection -> готовая система

вместо скрытого поиска зависимостей во время работы.

Не создавать Singleton или Service Locator только ради того, чтобы избежать передачи зависимости.

## 13. Dependency Injection

Для обычных C#-классов предпочтительно использовать constructor injection.

Пример:

~~~csharp
public SomeController(SomeModel model, SomeView view, ISomeInput input)
{
    _model = model;
    _view = view;
    _input = input;
}
~~~

Плюсы:

- зависимости видны сразу;
- класс проще тестировать;
- меньше скрытых зависимостей;
- Bootstrap контролирует сборку системы.

Для MonoBehaviour зависимости Unity-сцены могут передаваться через Inspector, если это естественно для Unity.

Не нужно пытаться построить полноценный DI-фреймворк для маленькой игры без необходимости.

## 14. Паттерны

Паттерны нужно выбирать по задаче.

Возможные примеры:

- Controller;
- Service;
- Model/View/Presenter;
- Strategy;
- Factory;
- State;
- Observer;
- Adapter;
- Command;
- другие подходящие паттерны.

Это не обязательный список и не обязательная архитектура.

Если выбранный паттерн неочевиден пользователю, ИИ должен объяснить:

1. Как называется паттерн.
2. Какую проблему он решает.
3. Почему он подходит именно здесь.
4. Какие у него минусы или дополнительные сложности.
5. Как он будет применён в конкретном коде.

Пользователь ещё изучает архитектурные паттерны. Если новая задача хорошо решается неизвестным ему паттерном, ИИ должен использовать возможность обучить его этому паттерну, а не просто молча выдать код.

## 15. Presenter

Presenter может использоваться, когда нужно отдельно связать состояние или данные механики с её визуальным представлением.

Например:

Model -> Presenter -> View

Presenter не обязан присутствовать в каждой системе.

Если прямое взаимодействие проще и не нарушает архитектуру, дополнительный Presenter не нужен.

## 16. Update, Tick и Unity lifecycle

Не следует без необходимости помещать всю логику игры непосредственно в Update MonoBehaviour.

Предпочтительно, чтобы MonoBehaviour являлся Unity-точкой входа, а основная логика находилась в обычных классах.

Например:

Unity Update
    ↓
Bootstrap / Controller
    ↓
Model / Service
    ↓
View

Если используется физика, учитывать различие между Update и FixedUpdate.

Не переносить физическую логику в Update только потому, что это проще написать.

## 17. События и Observer

События можно использовать для слабой связанности между системами, когда это действительно полезно.

Не следует заменять обычный прямой вызов событиями без причины.

При использовании событий необходимо понимать:

- кто публикует событие;
- кто подписывается;
- когда происходит отписка;
- кто владеет временем жизни подписки.

Избегать ситуации, когда события создают скрытую и трудно отслеживаемую цепочку выполнения.

## 18. Глобальное состояние

По умолчанию избегать:

- глобальных static-хранилищ состояния;
- Singleton для каждой системы;
- Service Locator;
- скрытого доступа к объектам через глобальные точки.

Предпочтительно явно передавать зависимости через Bootstrap.

Глобальное состояние допустимо, если оно действительно является частью архитектуры проекта и его использование оправдано.

## 19. Поиск зависимостей

Не использовать автоматический поиск объектов сцены вроде FindObjectOfType, FindAnyObjectByType и аналогичных методов для обычного связывания систем, если зависимость можно получить через Bootstrap или Inspector.

Это не абсолютный запрет.

Если динамический поиск действительно является частью задачи, его можно использовать, но нужно понимать его последствия.

## 20. Именование

Имена должны отражать ответственность класса.

Примеры:

- PlayerMoveController;
- HealthModel;
- ScorePresenter;
- BallHitService;
- GameplayBootstrap.

Не использовать бессмысленные названия вроде Manager, Helper, Utils или Handler, если название не объясняет реальную ответственность класса.

Если такое слово является частью точного и понятного имени, оно допустимо.

## 21. Организация файлов

Предпочтительно организовывать код по функциональности, а не складывать все классы одного типа в огромные глобальные папки.

Например:

Scripts/
    Features/
        Gameplay/
            Movement/
            Health/
            Score/
            Ball/

Это пример, а не жёсткая структура.

Если конкретный проект уже использует другой принцип, сохранять его.

## 22. Не переусложнять

Не создавать:

- интерфейс без необходимости;
- фабрику для одного new;
- сервис для двух строк логики;
- отдельный менеджер для каждой переменной;
- сложную систему событий вместо прямого вызова;
- глубокую иерархию классов;
- собственную физику вместо Unity Physics.

Архитектура должна помогать проекту, а не становиться отдельной проблемой.

## 23. Работа с неизвестным паттерном

Если для задачи подходит архитектурный паттерн, которого пользователь ещё не знает:

1. Назови паттерн.
2. Объясни его простыми словами.
3. Покажи небольшую схему взаимодействия.
4. Объясни, почему он подходит.
5. Покажи реализацию.
6. Объясни важные части реализации.
7. Не добавляй дополнительные паттерны только ради обучения.

Пользователь должен постепенно учиться распознавать архитектурные решения самостоятельно.

## 24. Формат работы ИИ

При разработке новой функциональности желательно работать по этапам:

1. Понять задачу.
2. Изучить существующую архитектуру.
3. Определить ответственности.
4. Определить зависимости.
5. Выбрать подход.
6. При необходимости назвать и объяснить паттерн.
7. Предложить структуру изменений.
8. Реализовать код.
9. Объяснить, куда помещается каждый скрипт.
10. Проверить возможные проблемы интеграции.
11. Предложить проверить результат в Unity.

Не нужно каждый раз писать длинную теорию.

Объяснение должно соответствовать сложности задачи.

## 25. Если запрос пользователя слишком короткий

Пользователь иногда формулирует задачу очень кратко.

Если из запроса однозначно понятен результат - не задавай лишних вопросов.

Если есть несколько существенно разных вариантов реализации, которые приведут к разной архитектуре или поведению, сначала задай уточняющий вопрос.

Не нужно спрашивать разрешение на каждую мелочь.

## 26. Изменение существующего кода

При исправлении существующей системы:

- не переписывай всё без необходимости;
- сохраняй существующие публичные контракты, если они используются;
- не меняй названия классов и файлов без причины;
- не проводи несвязанный рефакторинг;
- учитывай зависимости других систем;
- после изменения проверяй места использования изменённого API.

Если найден архитектурный недостаток, который не мешает текущей задаче, сообщи о нём отдельно.

## 27. Новая механика в пустом проекте

Если проект новый и архитектуры ещё нет:

1. Определи механику.
2. Раздели техническую Unity-часть и игровую логику там, где это действительно полезно.
3. Предпочти обычные C#-классы для логики.
4. Используй MonoBehaviour для Unity lifecycle, Inspector и Unity-компонентов.
5. Собери зависимости через Bootstrap.
6. Используй композицию и интерфейсы, если они дают реальную пользу.
7. Выбери паттерн только при наличии задачи, которую он решает.
8. Не создавай архитектурные слои заранее "на будущее".

## 28. Главное правило для Unity

Unity является частью архитектуры, а не врагом архитектуры.

Не нужно превращать каждый MonoBehaviour, Rigidbody, Collider, Animator или Transform в абстракцию.

Нужно разделять ответственность разумно:

- игровая логика - там, где её удобно тестировать и переиспользовать;
- Unity lifecycle - в MonoBehaviour;
- Unity Physics - в стандартных физических компонентах;
- визуальное представление - в View и связанных Unity-компонентах;
- сборка зависимостей - в Bootstrap.

## 29. Итоговая философия

> Не пытайся сделать проект похожим на идеальную архитектуру из учебника.

Архитектура выбирается из задачи.

Предпочтения пользователя:

- композиция вместо глубокой иерархии наследования;
- интерфейсы там, где они действительно отделяют контракт от реализации;
- обычные C#-классы вместо MonoBehaviour, если Unity lifecycle не нужен;
- Bootstrap как место сборки зависимостей;
- Controller для прямого управления механикой;
- Service для отдельной бизнес-логики механики;
- View для Unity-представления и технического взаимодействия;
- Unity Physics напрямую, когда это упрощает физику;
- минимальное количество лишних абстракций;
- понятный код;
- обучение новым архитектурным паттернам по мере необходимости.

Сначала пойми задачу.

Потом изучи архитектуру проекта.

Потом выбери подход.

Потом объясни важные решения.

И только после этого реализуй код.


## 30. Крупные изменения сцен — через Unity Editor C#

Для крупных работ, связанных с созданием или перестройкой сцен, предпочтительно использовать специальный Editor-скрипт на C#, который создаёт и настраивает объекты через Unity Editor API. Не следует вручную конструировать большой YAML-файл сцены, если ту же задачу можно надёжнее выполнить средствами редактора.

### Когда использовать Editor-скрипт

Считай работу крупной и используй Editor-скрипт, если задача включает одно или несколько условий:

- создание целого меню, HUD или другой заметной UI-системы;
- создание множества GameObject и компонентов;
- перестройку иерархии значительной части сцены;
- массовую настройку компонентов, якорей, ссылок, событий или других сериализованных полей;
- настройку сцены, которую нужно воспроизводимо применять к нескольким сценам или проектам;
- работу, где вручную легко ошибиться в fileID, ссылках на компоненты или структуре сериализованных данных.

Примеры: создание главного меню с кнопками и переходами, построение сложного HUD, массовая настройка объектов или генерация стартовой структуры сцены.

### Когда допустимо напрямую менять сцену или YAML

Для небольшого локального изменения допустимо отредактировать существующую сцену напрямую, в том числе её YAML, если:

- изменение ограничено небольшим числом понятных полей;
- нужные объекты и ссылки уже существуют;
- изменение не требует создания сложной иерархии;
- структура файла и зависимости изучены;
- риск повреждения сцены невелик.

Примеры: изменение одного уже существующего значения, включение уже настроенного объекта или корректировка простого положения элемента. Если сомневаешься, выбирай Editor-скрипт для более надёжного изменения.

### Требования к Editor-скрипту

1. Размещай редакторский инструмент в подходящей папке `Editor`, чтобы он не попадал в обычную игровую сборку.
2. Используй Unity Editor API для создания и изменения объектов, компонентов и их связей, а не пытайся имитировать сериализованный YAML вручную.
3. Перед созданием изучи сцену и проверь, нет ли уже нужных объектов. Повторный запуск не должен бесконтрольно создавать дубликаты.
4. По возможности поддерживай Undo через `Undo` API и корректно помечай изменённую сцену как изменённую.
5. Не перезаписывай сцену целиком без необходимости: изменяй только нужные объекты и настройки, сохраняя существующую работу.
6. Учитывай зависимости: компоненты, ресурсы, EventSystem, обработчики кнопок, ссылки на объекты, настройки Canvas и другие требуемые части.
7. Делай команды инструмента понятными и конкретными. Избегай опасного действия, которое без предупреждения удаляет или заменяет значительную часть сцены.
8. После генерации проверь код скрипта, используемые API, ожидаемую иерархию и ссылки. Если Unity Editor недоступен, прямо сообщи, что фактический запуск и проверка в редакторе не выполнялись.
9. Не оставляй одноразовый генератор в проекте автоматически. Если инструмент может быть полезен повторно, оставь его с понятным названием и назначением; если он одноразовый, обозначь это и удали после подтверждённого успешного применения, когда это безопасно.
10. Если пользователь должен запустить инструмент вручную в Unity, объясни точный путь к команде меню и что проверить после запуска.

### Рабочий порядок для крупной работы со сценой

1. Изучи сцену, связанные скрипты, префабы и ресурсы.
2. Определи, какие объекты нужно создать или изменить и какие связи должны существовать.
3. Подготовь Editor-скрипт, который выполняет конкретную операцию через Unity API.
4. Проверь, что скрипт не создаёт дубликаты и не повреждает существующую сцену при повторном запуске.
5. Примени его в Unity Editor, если среда выполнения доступна; иначе предоставь скрипт и инструкции по запуску, не утверждая, что он уже выполнен.
6. Проверь результат в сцене, ссылки компонентов и поведение в Play Mode там, где это относится к задаче.
7. После успешной проверки реши, следует ли оставить инструмент для повторного использования.

### Ограничения и архитектура

Editor-скрипт — это инструмент разработки, а не игровая логика. Он не должен подменять Runtime-классы, Bootstrap, Model, Service, Controller или View. Создание объектов во время разработки через Editor API и создание объектов во время игры — разные задачи; выбирай способ в зависимости от того, когда объекты должны появляться.

Предпочтение Editor-скриптам для крупных изменений сцен не является абсолютным запретом на YAML. Небольшие и хорошо понятные правки сериализованных данных остаются допустимыми, если это безопаснее и проще. Главное — надёжность, сохранение существующей сцены и проверяемый результат.
